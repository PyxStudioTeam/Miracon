# Инструкция по передаче по FTP

Для простой установки по шагам сначала используйте [краткую инструкцию для
cPanel на русском языке](simple-hosting-setup-ru.md). Этот документ нужен как
подробный справочник и инструкция по поиску неисправностей.

В этой инструкции описаны файлы и подтверждающие материалы, передаваемые
команде хостинга для автономного развертывания PostgreSQL/Passenger. Это
инструкция по передаче по FTP, а не руководство по работе с cPanel. Загрузку по
FTP, настройку cPanel, доступ к PostgreSQL, DNS, TLS и приемку в рабочей среде
выполняет команда хостинга, используя предоставленные ею значения.

## 1. Данные, которые должна предоставить команда хостинга

До принятия передачи получите следующие значения. Не подставляйте их наугад:

- `HOST_APP_ROOT`: корень приложения cPanel и каталог, в который будет распакован
  архив релиза.
- `HOST_MEDIA_ROOT`: абсолютный доступный для записи путь вне `dist/`, не являющийся
  символической ссылкой.
- `HOST_MEDIA_STATE`: абсолютный доступный для записи путь к файлу состояния вне
  `dist/`.
- `DATABASE_URL`: строка подключения к целевой базе PostgreSQL.
- `PUBLIC_SITE_URL`: канонический HTTPS-адрес.
- `HOST_HEALTH_URL`: URL проверки работоспособности по HTTPS после настройки
  приложения.
- Поддерживаемые учетной записью процедуры для startup-файла Passenger,
  переменных среды менеджера приложений, перезапуска, резервного копирования,
  TLS и доступную версию Node не ниже `>=22.12.0`.

Остановитесь: не создавайте пакет с привязанными к хосту командами и ничего не
загружайте, пока команда не подтвердит эти значения, Node `>=22.12.0`, Passenger,
PostgreSQL, доступный диск и ОЗУ. Node 22.23 подходит, если именно эту версию
предлагает cPanel. Фактические версии, ресурсы, корень приложения, учетные данные
базы, порт и настройки cPanel должны быть подтверждены командой хостинга.

## 2. Локальные проверки и передаваемые артефакты

Запустите эти команды из корня репозитория на рабочей станции миграции. Вместе с
передачей сохраните вывод команд, идентификаторы снимков, количества и манифесты
SHA-256.

```bash
npm ci
npm run release:verify
DATABASE_TEST_ALLOW_RESET=1 \
DATABASE_TEST_URL=postgresql://USER:PASSWORD@127.0.0.1:5432/miracon_test \
npm run standalone:test:db
```

Остановитесь, если какая-либо команда завершилась ошибкой, `npm run build` не
создала `dist/server/entry.mjs` или локальные подтверждающие материалы не
сохранены. Это только локальные результаты. Они не подтверждают состояние среды
хостинга клиента. `standalone:test:db` разрешено запускать только с отдельной
одноразовой базой, имя которой содержит маркер `test`, `testing`, `ci`,
`disposable` или `tmp`; никогда не указывайте базу разработки, staging или
production.

Создайте архив релиза. Реализованный упаковщик включает `app.js`, `dist`,
`package.json`, `package-lock.json`, миграции PostgreSQL,
`scripts/postgres-migrate.mjs`, `scripts/provision-admin.mjs`,
`scripts/supabase-import.mjs`, `scripts/verify-media-state.mjs`, а также модули
среды выполнения, транзитивно требуемые для `migration:import`,
`migration:validate` и `migration:media:verify`:
`scripts/migration/{import-artifacts,import-database,import-preparation,media-filesystem,media-paths,media-state-verifier,parity-report,postgres-import,transfer-contract,validate-transfer}.mjs`.
Он намеренно исключает инструменты экспорта с автономной рабочей станции и
передачи медиафайлов, `node_modules`, секреты, тесты, `public` и другие материалы
для разработки и развертывания. Собранные ресурсы `dist/client` включены.
Исключение исходного `public/` является намеренным.

```bash
npm run release:package -- <RELEASE_DIR>
```

Передайте `RELEASE_DIR/` как архив релиза или заархивируйте его без изменения
содержимого. Передайте также его `release-manifest.json` и зафиксированную версию
приложения. Остановитесь, если манифест отсутствует или архив содержит `.env`,
ключи, пароли, учетные данные service-role или `node_modules`.

Экспортируйте снимок содержимого Supabase и манифест, используя учетные данные,
предоставленные только для этой автономной передачи:

```bash
set SUPABASE_SOURCE_URL=<SOURCE_SUPABASE_HTTPS_URL>
set SUPABASE_SOURCE_SERVICE_ROLE_KEY=<OFFLINE_TRANSFER_ONLY_SERVICE_ROLE_KEY>
set PUBLIC_SITE_URL=<CURRENT_CANONICAL_ORIGIN>
npm run migration:export -- --output=<EXPORT_DIR> --site-origin=<CURRENT_CANONICAL_ORIGIN>
```

Если `set` неприменима, используйте эквивалентный синтаксис переменных среды для
вашей оболочки. Для экспорта требуется, чтобы `SUPABASE_SOURCE_URL` использовал
HTTPS; учетные данные в URL отклоняются. Передайте `EXPORT_DIR/snapshot.json` и
`EXPORT_DIR/manifest.json`. Никогда не помещайте service-role key в релиз, среду
сайта или любую переменную `PUBLIC_*`. После передачи удалите его из среды
рабочей станции.

Перенесите используемые медиафайлы в проверенное локальное дерево медиафайлов и
файл состояния:

```bash
npm run migration:media -- --input=<EXPORT_DIR> --media-root=<ABSOLUTE_LOCAL_MEDIA_ROOT> --state=<ABSOLUTE_LOCAL_MEDIA_STATE> --dry-run
npm run migration:media -- --input=<EXPORT_DIR> --media-root=<ABSOLUTE_LOCAL_MEDIA_ROOT> --state=<ABSOLUTE_LOCAL_MEDIA_STATE>
```

Запуск без dry-run использует те же переменные среды автономной передачи:
`SUPABASE_SOURCE_URL` и `SUPABASE_SOURCE_SERVICE_ROLE_KEY`. Используйте `--resume`
только для продолжения передачи того же снимка и файла состояния:

```bash
npm run migration:media -- --input=<EXPORT_DIR> --media-root=<ABSOLUTE_LOCAL_MEDIA_ROOT> --state=<ABSOLUTE_LOCAL_MEDIA_STATE> --resume
```

Остановитесь, если dry-run сообщает о неожиданных кандидатах, в передаче остаются
незавершенные записи, проверка контрольной суммы, подписи или размера завершается
ошибкой либо идентификатор снимка в состоянии не совпадает с `snapshot.json`.
Передайте полное проверенное дерево медиафайлов и JSON состояния медиафайлов.
Медиафайлы не входят в `dist/` или архив релиза.

## 3. Установка и импорт командой хостинга

Команда хостинга размещает архив релиза и переданные артефакты медиафайлов и
состояния с помощью утвержденного процесса передачи. Эта инструкция не задает
пути на хосте.

Внутри `<HOST_APP_ROOT>`, в подтвержденной среде Node `>=22.12.0` платформы
хостинга (Node 22.23 также подходит, если доступен):

```bash
cd <HOST_APP_ROOT>
npm ci --omit=dev
```

Не загружайте `node_modules`. `argon2` является нативной зависимостью: установите
его на сервере с подтвержденной версией Node, чтобы npm выбрал или собрал бинарный файл,
совместимый с ABI сервера. Остановитесь, если установка не может собрать или
загрузить `argon2`. Не копируйте `node_modules` с рабочей станции в качестве
обходного решения. Установка производственных зависимостей является этапом
приемки на хостинге, который нельзя подтвердить локально по архиву.

Настройте переменные, предназначенные только для сервера, через поддерживаемый
платформой хостинга механизм задания среды:

```dotenv
DATABASE_URL=<TARGET_POSTGRES_CONNECTION_STRING>
MEDIA_ROOT=<ABSOLUTE_HOST_MEDIA_ROOT>
PUBLIC_SITE_URL=<CANONICAL_HTTPS_ORIGIN>
CONTACT_DIGEST_SECRET=<INDEPENDENT_SECRET_AT_LEAST_32_CHARACTERS>
CONTACT_SMTP_ENABLED=false
```

`CONTACT_DIGEST_SECRET` обязателен в production и должен храниться только на
сервере вне релиза и `public_html`. Уведомления SMTP по умолчанию отключены. Если
они отдельно одобрены, задайте полный серверный набор
`CONTACT_SMTP_ENABLED=true`, `CONTACT_SMTP_HOST`, `CONTACT_SMTP_PORT`,
`CONTACT_SMTP_USER`, `CONTACT_SMTP_PASSWORD`, `CONTACT_SMTP_FROM` и
`CONTACT_SMTP_TO`; используйте только порт 465 с implicit TLS или 587 с
обязательным STARTTLS. Не добавляйте к этим именам префикс `PUBLIC_`.

Не настраивайте `SUPABASE_SOURCE_SERVICE_ROLE_KEY` в среде выполнения сайта. Эта
переменная предназначена только для автономной передачи. Среда выполнения сайта
использует PostgreSQL и локальные медиафайлы и не должна получать учетные данные
service-role.

Скопируйте проверенное дерево медиафайлов в `<HOST_MEDIA_ROOT>`, а файл состояния
скопируйте в `<HOST_MEDIA_STATE>`. Убедитесь, что оба пути доступны для записи,
постоянны, находятся вне `dist/`, охватываются политикой резервного копирования
команды хостинга и не являются символическими ссылками.

До любого импорта базы проверьте файлы в том виде, в котором они находятся после
передачи по FTP:

```bash
cd <HOST_APP_ROOT>
npm run migration:media:verify -- --media-root=<HOST_MEDIA_ROOT> --state=<HOST_MEDIA_STATE>
```

Эта команда не использует учетные данные и не выполняет сетевых запросов или
запросов к базе данных. Для каждой записи состояния она использует относительный
путь внутри `<HOST_MEDIA_ROOT>`, а не абсолютный путь, доступный только на рабочей
станции, отклоняет дублирующиеся пути, выходы за пределы каталога и символические
ссылки, а также хеширует каждый ожидаемый файл. Остановитесь, если идентичность
или завершенность состояния, количество байтов либо SHA-256 не совпадают.

Запустите упорядоченную миграцию PostgreSQL, затем создайте одну учетную запись
администратора:

```bash
cd <HOST_APP_ROOT>
npm run postgres:migrate
printf '%s' '<ADMIN_PASSWORD_FROM_SECURE_INPUT>' | npm run admin:provision -- --email=<ADMIN_EMAIL> --password-stdin
```

Используйте `--rotate` только при замене существующего администратора.
Остановитесь при расхождении миграций, отсутствии `DATABASE_URL`, ошибке
подключения или наличии существующего администратора, если ротация явно не
разрешена. Не помещайте пароль в историю оболочки или релиз.

Выполните импорт и проверку в следующем порядке:

```bash
npm run migration:import -- --input=<EXPORT_DIR> --media-state=<HOST_MEDIA_STATE> --dry-run
npm run migration:import -- --input=<EXPORT_DIR> --media-state=<HOST_MEDIA_STATE>
npm run migration:validate -- --input=<EXPORT_DIR> --media-state=<HOST_MEDIA_STATE>
```

Остановитесь, если количества в dry-run, контрольные суммы миграций, завершенные
записи медиафайлов или проверка соответствия не совпадают с переданными
манифестами. `migration:validate` выполняет строгую проверку: дополнительные
проекты, изображения проектов или строки медиафайлов считаются ошибкой так же,
как отсутствующие или измененные строки. Не открывайте публичный трафик при
неудачной проверке.

## 4. Проверки передачи для Passenger

Релиз содержит `app.js`, который импортирует `dist/server/entry.mjs`. Настройте
Passenger на использование `app.js` или получите явное подтверждение, что
настройка startup-file на платформе предоставляет эквивалентную возможность,
укажите подтвержденный хостингом Node `>=22.12.0` (Node 22.23 подходит, если
доступен) и переданный платформой хостинга Passenger `PORT`. Не
задавайте порт жестко.

Если перед включением Passenger команде хостинга нужна проверка запуска в
foreground, выполните startup-скрипт репозитория со значением порта,
предоставленным платформой:

```bash
PORT=<PASSENGER_SUPPLIED_PORT> npm run start
```

Остановитесь, если процесс завершился или не может привязаться к переданному
порту. Не подставляйте выдуманный порт. Passenger должен предоставить фактический
порт среды выполнения.

Убедитесь, что `<HOST_APP_ROOT>/tmp` доступен для записи, затем используйте
утвержденный платформой механизм перезапуска Passenger, создав или обновив:

```text
<HOST_APP_ROOT>/tmp/restart.txt
```

После перезапуска запросите настроенный URL проверки работоспособности по HTTPS:

```bash
curl -fsS <HOST_HEALTH_URL>
```

Остановитесь, если в журналах Passenger есть ошибки запуска, ABI, среды,
разрешений или базы данных либо проверка работоспособности по HTTPS неуспешна.
При приемке команда хостинга также должна выполнить smoke-тест публичной главной
страницы, одного опубликованного проекта, `/el/`, входа администратора,
сохранения и повторной загрузки в админ-панели, предпросмотра, загрузки и выхода.
Фактический результат проверки по HTTPS и в браузере является подтверждением со
стороны хостинга, а не результатом, который этот репозиторий может установить
автономно.

## 5. Граница переключения и отката

Оставьте существующий сайт Vercel/Supabase работающим и сохраняйте его
базу/хранилище и учетные данные, пока команда хостинга не одобрит проверки HTTPS
и smoke-тесты админ-панели и публичной части. Перед финальным экспортом заморозьте
изменения содержимого. Если после экспорта выполнялись записи, эти изменения не
входят в передачу и могут быть потеряны. Повторите экспорт, передачу медиафайлов,
импорт и проверку вместо того, чтобы молча принимать расхождение.

Переключайте трафик только после успешного завершения проверки и smoke-тестов.
Для отката верните трафик и DNS на сохраненный источник Vercel и остановите либо
изолируйте новое приложение Passenger. Сохраните неудачный релиз, журналы,
снимок, манифесты, состояние медиафайлов и резервную копию базы для расследования.
Запускайте откат при неудачной проверке работоспособности, ошибке аутентификации
или сохранения в админ-панели, ошибках публичных медиафайлов, несоответствии,
повреждении данных, повторных перезапусках Passenger или неприемлемых ошибках
ресурсов/разрешений. Храните артефакты отката, пока команда хостинга не утвердит
срок хранения и не подтвердит проверенную резервную копию. Не удаляйте старый
путь Supabase/Vercel в рамках этой передачи по FTP.

## Граница ответственности

Передача этого репозитория не включает загрузку по FTP, доступ к cPanel,
настройку DNS/TLS, развертывание PostgreSQL, настройку firewall или резервного
копирования и управление рабочим трафиком. Команда хостинга предоставляет эти
значения и выполняет соответствующие действия внутри своей среды. Наша
ответственность ограничивается передачей артефактов и данных по FTP. Локальные
тесты и манифесты подтверждают только целостность артефактов и соответствие
контракту миграции. Без реальной среды хостинга они не могут подтвердить
совместимость с cPanel/Passenger. Команда хостинга самостоятельно настраивает
Passenger, PostgreSQL, DNS и TLS.
